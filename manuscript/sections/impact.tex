\section{Impact}
\label{sec:impact}

\subsection{Practical value for operations planning}
FHOPS reduces the cost of moving from ad hoc local models to comparable, auditable planning studies. The practical value is not one ``best'' solver run, but a repeatable workflow that keeps inputs, constraints, solver settings, and evaluation outputs aligned across planning cycles.
For planning teams, this supports more defensible schedule revisions because performance differences can be tied to declared assumptions rather than undocumented preprocessing or solver-configuration changes.

\subsection{Research value in the manuscript sequence}
Relative to the review paper \cite{jaffray2026systematic}, this manuscript contributes executable infrastructure: a shared scenario contract, a traceable formulation, and reproducible baseline evidence. Relative to companion modelling studies, it provides the stable software and data baseline used to test methodological questions (e.g., rolling-horizon configuration effects), so platform and modelling claims can be evaluated separately. The first companion study builds on that baseline: Chapter~4 of Jaffray's MASc thesis evaluates rolling-horizon machine-scheduling design across three BC operating contexts (North-Island, Kamloops, and Prince-George Timber Supply Areas) and three problem sizes \cite{jaffray2026thesis}.

\subsection{Maturity and current scope}
The current release is an early public platform baseline. It demonstrates reproducible scheduling experiments on public BC reference scenarios and synthetic tiers (Section~\ref{sec:illustrative-example}), but does not claim broad external deployment evidence. Since this manuscript was first submitted, a very early-alpha tactical--operational planning layer has been published as a pre-release (FHOPS~1.1.0a1). It covers block harvest selection, product flows to mills and terminals, transport arcs, and delivered-cost, profit, or net-present-value objectives, with a hand-off of tactical commitments to the operational scheduler documented here. That layer is provisional, is not part of the stable release described in this paper, and is not evaluated here.

\subsection{Transferability and limits}
FHOPS is structured to support transfer to new contexts through scenario and parameter updates rather than solver rewrites. Four current limits remain explicit:
\begin{itemize}
  \item Validation breadth is still centred on a single harvest-system archetype (BC ground-based cut-to-length); skyline, helicopter, tethered, and salvage systems are not yet validated here and make no claim of generality beyond that archetype.
  \item Runtime comparisons are environment-dependent and should be interpreted as within-study baselines. Seeded heuristic results are bit-reproducible on a fixed platform, but last-bit floating-point differences between NumPy or Python builds can change an SA acceptance decision and hence the search trajectory; the published assets therefore record their platform (\breakpath{notes/softwarex_assets_v101_env.txt} and \breakpath{docs/softwarex/assets/benchmark_runs.log}).
  \item Warm-start MIP integration is implemented (HiGHS and Gurobi), but decisive performance gains at larger stress cases are not yet claimed.
  \item Delay effects are reported as utilisation and production losses in playback; schedule-level cost outputs currently cover mobilisation only and do not yet convert delays into standby or delay costs.
\end{itemize}

These limits keep the manuscript's claims aligned with demonstrated evidence.

\section{Software description}
\label{sec:software-description}

FHOPS is organized around the core operational scheduling question: given a set of blocks, machine resources, shift calendars, and mobilization constraints, what assignments should be made, in which sequence, and with what expected production and cost consequences. This question sits below tactical-operational planning in the planning hierarchy: which blocks are harvested, and with which harvest system and prescription, is decided upstream, and those decisions fix the assortment volumes (and therefore gross revenue) that the operational schedule must deliver. FHOPS therefore takes them as inputs and optimises how the resulting work is executed, rather than maximising profit. The scheduling scope ends at the landing: loader output is counted in truckload-sized batches (\textbf{E9}), but haul transport (truck fleets, dispatching, and delivery to mills) is outside the operational model. The software architecture is therefore defined by planning entities and decision logic first, and by implementation boundaries second.

\subsection{Operational entities and planning context}
The platform uses a typed scenario contract allowing solver results to be compared on fixed operational inputs:
\begin{itemize}
  \item \textbf{Blocks and windows}: harvest volumes, treatment windows, and system requirements.
  \item \textbf{Machines and roles}: role-specific production rates, availability, and compatibility. For the reference ladder, rates are derived from published productivity models and include each source model's delay or utilisation allowance; stochastic disruptions are handled separately in playback (Section~\ref{sec:illustrative-example}).
  \item \textbf{Shift calendar}: day-shift time grid used for assignment and production accounting; machine availability flags $A_{m,s}$ remove planned downtime (e.g., maintenance or crew days off) from the schedule.
  \item \textbf{Landings and mobilization}: movement penalties and daily landing capacities.
  \item \textbf{Constraint metadata}: sequencing prerequisites, role activation conditions, and completion balances.
\end{itemize}

The role-activation metadata also lets users compare coupled and decoupled harvesting systems on the same scenario. A per-role head-start (in shifts of upstream output) sets the staged buffer $B_{r,b}$ in \textbf{E8}: a positive head-start represents a decoupled system in which, for example, a roadside processor starts only once a deck has accumulated, whereas a zero head-start approximates a coupled (hot) system limited only by the one-shift staging lag of \textbf{E7}. The reference ladder uses zero head-start for processing and loading, apart from the loader's truckload batch.

FHOPS ships a public BC ground-based reference ladder (tiny7, small21, med42) that scales from 7/2 to 21/6 to 42/12 (days/blocks) while keeping one operational archetype.

This addresses a central review finding \cite{jaffray2026systematic}: transfer fails when assumptions are embedded in bespoke code rather than explicit scenario data. Generalizability is supported structurally through this scenario contract, which separates operational assumptions from solver logic. Empirical validation across additional system families remains future work.

\subsection{Solution methods for operational decisions}
FHOPS provides complementary solver families for different planning horizons and time budgets:
\begin{itemize}
  \item \textbf{Metaheuristic solvers (SA/ILS/Tabu)} provide practical schedule candidates for larger instances where rapid re-solving is needed.
  \item \textbf{Mixed-integer linear programming (MILP)} provides an exact baseline where tractable, supporting verification and sensitivity analysis.
  \item \textbf{Playback evaluation} re-simulates solved schedules under deterministic and stochastic conditions to quantify utilization, continuity, and disruption effects.
\end{itemize}

This reflects established forestry operations research (OR) practice: exact models support formulation clarity and benchmark bounds, while heuristics support larger-scale operational runs \cite{paradis2018bilevel,nelson2003forestmodels}.

Warm-start support is implemented for MIP, but this paper does not claim decisive wall-clock gains on med42/large84 stress contexts. For periodic re-planning (for example, after weather or delay disruptions), FHOPS also ships a rolling-horizon driver (\texttt{fhops plan rolling}) that re-solves successive planning windows with the SA or MILP solver while locking near-term decisions; rolling-horizon design itself (horizon length and re-optimisation frequency) is evaluated in the companion study \cite{jaffray2026thesis}.

\subsection*{Objective-weight and sign convention}
Both the MILP baseline and the SA/ILS/Tabu heuristics maximise the same weighted score defined by the \textbf{OBJ} expression in the canonical formulation below: production reward minus mobilisation, transition, and landing-surplus penalties minus a per-violation penalty on hard feasibility constraints. The base weights are part of the scenario contract (\texttt{objective\_weights} in each \texttt{scenario.yaml}) and default to $\omega_{\text{prod}}=1.0$, $\omega_{\text{mob}}=1.0$, $\omega_{\text{trans}}=0.0$, $\omega_{\text{land}}=0.0$. The shipped calibration is three-tier. All four reference scenarios (tiny7, small21, med42, large84) declare $\omega_{\text{prod}}=1.0$, $\omega_{\text{mob}}=0.5$ in their scenario contracts. The two smallest reference scenarios (tiny7, small21) additionally auto-apply reduced relocation weights, $\omega_{\text{prod}}=1.0$, $\omega_{\text{mob}}=0.2$, $\omega_{\text{trans}}=0.1$, $\omega_{\text{land}}=0.05$, inside the SA/ILS/Tabu drivers to encourage exploration on instances where the full mobilisation penalty would trap the search in a degenerate zero-production basin. The synthetic scaling tiers (small/medium/large) declare no \texttt{objective\_weights} and therefore use the defaults. A negative objective value therefore marks a penalty- or mobilisation-dominated instance, not a change of optimisation sense: the more positive (less negative) score is always the better solution, and the relative ordering within a scenario is the quantity the benchmark tables report.

\subsection{Architecture and implementation boundaries}
Internally, FHOPS separates four concerns:
\begin{enumerate}
  \item \textbf{Scenario layer}: ingestion and validation of planning entities.
  \item \textbf{Optimization layer}: heuristic and MILP solvers sharing common scenario inputs.
  \item \textbf{Evaluation layer}: playback and key performance indicators (KPI) computation for solved schedules.
  \item \textbf{Reporting layer}: generation of tables/figures used in manuscript and documentation outputs.
\end{enumerate}

Figure~\ref{fig:fhops-prisma-overview} summarises how these layers connect: versioned scenario contracts and reference/synthetic datasets enter the FHOPS core for validation, solving, and evaluation, and the asset scripts emit the shared tables and figures that feed both this manuscript and the public documentation.

The software is available through Python modules and command-line wrappers. Interface choice is secondary to preserving equivalent, traceable evidence across runs. FHOPS is released under an MIT license, with source code, datasets, and experiment pipelines in a public repository to support reuse and independent verification.

\subsection{Reproducible evidence pipeline}
Manuscript evidence comes from versioned benchmark, tuning, playback, costing, and scaling assets produced by the same platform layers. Run logs and artifact paths provide provenance for each reported value.

This arrangement is deliberate in the manuscript sequence: the review identifies missing reproducibility infrastructure \cite{jaffray2026systematic}, this paper contributes it as reusable software, and companion modelling studies can focus on method questions without redefining data contracts or reporting conventions.
